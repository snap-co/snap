# Platform-owned effects and IO-free operations

Transport invokes operations, operations read and stage changes through Store, and successful Store commits signal Controllers. External effects and nondeterministic inputs belong to platform-supplied capabilities rather than ambient IO inside operation code, so the same application behavior can run on real or controlled testing platforms.

Application behavior depends on portable shared interfaces and modules, not concrete platform implementations. The host selects platform capabilities and connects them to the application. Store and Transport are the current shared interfaces for storage and invocation; modules do not each require a paired platform package.

Portable contracts and module behavior live under `crates/`. Transport owns its portable host engine and feature-selected native execution and carriers in the same package. Other platform implementations live under `crates/platform/`. Native features are excluded on Wasm; portable behavior remains `no_std` with `alloc`. Browser WebAssembly is an environment distinct from other WebAssembly hosts; future Swift or Kotlin UI integration may need its own host integration, but foreign-language bindings and ABI mechanics are deferred. Dependency-role and portable-target checks enforce the boundary independently of directory names.

Package names use `snap-` followed by the capability or implementation, such as `snap-transport` and `snap-store-sqlite`, without requiring another `platform` prefix. Document replication belongs to the portable Document module. Store owns shared residency machinery; Transport's generic host coordinates residency requirements and drives controller reconciliation, independent of Document. Modules supply their data declarations and domain-specific controller behavior. The native Transport executor drives the portable loop contract without a production dependency on Document. Each application's host selects its carriers and supplies its definitions and external capabilities. OAuth is a platform capability, not an application entrypoint.

Native applications compose through `snap_transport::native::Server` and its serialized transaction handle. The `native-client` feature selects TCP client IO; `native-server` adds server execution and HTTP/WebSocket carriers. An HTTP-only host need not open a TCP listener. Custom execution loops and controlled platforms can use the native carrier and queue APIs directly. Carriers exchange shared Transport commands and responses through the domain-independent dispatch interface; operation execution, logical-connection semantics, Store residency and application permissions remain outside the carrier. Alternative protocols can use that interface without depending on Document or Identity behavior. Compatibility packages and parallel names for these implementations are unnecessary.

TCP/CBOR and WebSocket/JSON use the same carrier handoff contract. A driver listens, accepts, reads, decodes and queues commands, then encodes and writes published responses. Queue submission does not execute or wait for an operation. Host owns admission, execution, credential preparation and response policy. Socket handling and application execution can progress independently, including physical teardown while application work is busy. Separate threads are a host choice, not a requirement of the portable interface.

Production statically links the host, platform and application while preserving their dependency separation. Loading and unloading application code without restarting the host is a development-only goal, not a current requirement. Dynamic-library formats, ABI stability, reload lifecycle and state handoff are deferred; organizing dependencies does not require selecting those mechanisms now.

For now, portable code, compiler checks, dependency rules and agent instructions enforce this architecture cooperatively; this is not a sandbox guarantee for arbitrary native code. Deterministic simulation is a long-term goal, not a strict current replay or same-seed guarantee, and mostly single-threaded execution is sufficient for present work.

The blocking host holds one FIFO lane through admission, Store commit, commit notification, synchronous controller passes, resource cleanup and completion. Controllers observe committed Store resources and may perform host-supplied IO; a controller failure cannot undo a committed transaction. Persisted resource state supports explicit retry and recovery, while in-process notifications alone do not promise durable delivery. Async controller scheduling, parallelism, distribution, MVCC, isolation options and Viewstamped Replication remain undecided.
