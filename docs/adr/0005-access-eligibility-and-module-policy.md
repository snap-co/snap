# Access eligibility and module policy

Access is a shared framework ACL module for registered resources, not a Document-specific permission feature. It marks resources eligible; it does not itself manage residency or send them to clients. Framework and module code can use viewer-or-higher eligibility to populate server residency manifests as soon as an identity creates a logical connection. Modules describe their data and translate eligible resources into generic Store requests rather than applications implementing separate ACL-driven loading machinery.

ACL grants and access links are framework-managed. Grant and revoke operations are invoked through Transport and perform ordinary transactional Store writes. Editor eligibility can satisfy an operation guard such as document mutation, but the owning domain still validates the requested change, such as allowing a user to edit their own messages but not another user's. Managers can administer lower-level grants; granting or revoking manager roles requires an owner. Raw ACL grant lists are not ordinary application data, and application-specific permissions remain separate from framework eligibility.

Clients fetch eligible resources, or the owning module supplies its own push or subscription mechanism and client representation. A Document synchronization request can report client holdings so the module supplies missing or stale data; this client manifest is distinct from server residency demand. Scoped synchronization and subscription optimizations are deferred. Access-link behavior remains to be clarified; this decision does not select a blob driver, Controller design or distributed execution model.
